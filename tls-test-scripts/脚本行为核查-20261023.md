# TLS 测试脚本行为核查

- 日期：2026-10-23
- 目的：确认“用例通过”来自被测实现的真实行为，而不是脚本断言过宽或空结果也算通过。
- 方法：静态检查断言与退出码 → 用独立工具（tshark）交叉验证 pcap 结论 → 变异测试（故意让服务端不支持预期组，看用例是否失败）。

## 一、独立工具交叉验证

以 TLS-1-1 的 `tls-1-1-kyber512.pcap` 为例，用 tshark 4.2.2（与自研解析器完全独立）复核：

```sh
tshark -r tls-1-1-kyber512.pcap -d tcp.port==8080,tls \
  -Y 'tls.handshake.type==1' -T fields \
  -e tls.handshake.extensions_supported_group \
  -e tls.handshake.extensions_key_share_key_exchange_length \
  -e tls.record.length
```

结果：`0xfe34`、`865`、`1049`；ServerHello 的 key_share 长度为 `897`。与脚本使用的 `tools/tshark_check.sh` 输出一致（组 0xfe34、CH 865、SH 897、ClientHello 记录 1049 字节）。解析结论直接来自 tshark，不是自研解析器。

## 二、发现并修复的问题

| 位置 | 问题 | 修复 |
|---|---|---|
| TLS-1-8 / 1-11 / 3-2 | tshark 未按 8080 端口解码，且“无匹配包”时退出码仍是 0，步骤恒 PASS | 增加 `-d tcp.port==<端口>,tls`，并断言 Alert `desc=70/40`、`tls.app_data` 至少 1 条 |
| TLS-1-8 第 1 步 | 只要求 openssl 非 0 退出，连接失败也会 PASS | 增加断言 `alert protocol version` / `alert number 70` |
| TLS-1-10 第 4 步 | 解析命令带 `|| true`，pcap 为空也 PASS | 去掉 `|| true`，并断言抓到 ClientHello |
| TLS-1-1/1-2/1-3/1-4 | `Used .*Kyber\|Server response` 过宽，组不对也可能匹配 | 收紧为只匹配 `Used .*<对应组>` |
| TLS-1-5/1-6/3-2 | `Server response\|代码执行时间` 过宽 | 收紧为 `Server response` |
| TLS-1-9 第 1 步 | `HelloRetryRequest\|Used X25519`，实际客户端不打印 HRR，只剩后半段 | 改为 `Used X25519`，并在 pcap 步骤增加“ServerHello 共 2 条” |
| TLS-1-12 / 1-6 | 长度断言只匹配 `865` 这类裸数字，可能命中 IP/端口 | 改为 `CH key_share:.*长度=865`、`SH key_share:.*长度=897` |
| TLS-2-5 | 资源采样步骤无断言 | 增加 `VmRSS`、`VmHWM`、`Threads`、`RSS` 断言 |
| TLS-2-7 | 中间盒只校验成功率文本，未校验总数 | 每个策略增加“成功+失败 = 200”校验 |
| TLS-1-13 负向 | 只看退出码非 0，服务端没起来也会判 PASS | 要求输出包含握手/TLS 错误文本 |
| `run_all.sh` | `NO-RESULT`/`UNKNOWN`/服务端侧 SSH 失败时退出码仍为 0 | 分别记为 `NO-RESULT`、`SERVER-SIDE-ERROR`，任一出现即退出 1 |
| `lib.sh` | 用例未执行任何步骤时可能判 PASS | `TOTAL=0 且 SKIP=0` 判 FAIL |
| `server-endpoints.sh` | 记的是 setsid 包装进程的 PID，`stop` 实际杀不掉；端口被 root 进程占用时静默跳过 | 改为按端口从 `ss -ltnp` 解析真实 PID；无权限时提示用 sudo |

## 三、变异测试（证明脚本会发现错误）

把服务端 8080 临时改成只支持 X25519（`-kex X25519`），再跑两条客户端用例：

| 用例 | 预期 | 实际 |
|---|---|---|
| TLS-1-1（客户端只提供 SM2Kyber512） | FAIL | **FAIL**：握手失败，`Used .*Kyber512` 不匹配 |
| TLS-1-6（客户端默认组，服务端选 X25519） | FAIL | **FAIL**：握手本身成功，但 pcap 断言 “SH 长度 897 / 组 0xfe34” 不匹配 |

恢复 8080 默认组后，两条用例重新 **PASS**。说明断言确实绑定在报文内容上，不是只看进程是否退出 0。

## 四、仍存在的边界

- 抓包类断言依赖 root/CAP_NET_RAW。没有权限时这些步骤统一记 SKIP（不会误判 FAIL），结论为“降级通过”；完整验收必须用 `sudo`。
- TLS-2-5 的资源数值本身是测量值，脚本只校验“采到了数据”，性能阈值应在报告里按课题指标另行判定。
- TLS-1-13 的四模式是“编译期 ProtocolType”决定的，部署阶段预编译了 KEM 变体；若二进制缺失会记 SKIP 并提示重新部署。

## 五、给第三方测试的建议

- 用 Wireshark/tshark 对 `captures/*.pcap` 做独立复核（组号、key_share 长度、Alert），不要只引用自研解析器的输出。
- 保留 `commands.log` 与 `output.log`，确保“输入 → 输出 → 断言”可追溯。
- 变异测试的结论可写入测试报告的“测试有效性说明”，证明用例具备发现缺陷的能力。
