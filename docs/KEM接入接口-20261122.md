# KEM 接入接口（为后续两种 KEM 预留）

日期：2026-11-22
适用范围：TLS KEX、ServerKeyGen、KEM 证书、pqc/pqcertlab/pqkemkey 工具链。

## 1. 结论

后续新增 C 语言 KEM 时，**不需要改 `crypto/tls`**：

1. 实现一个 `pq_alg` 描述符和 `keygen / pub_from_sk / encaps / decaps`；
2. 在 `pq_registry.c` 的 `pq_builtin[]` 加一行，或服务启动前调用
   `pq_alg_register()`；
3. 用 `KEMTLSKEXAlg` 选择 KEX/ServerKeyGen 算法；
4. 用 `KEMTLSKEMAlg` + 证书 `.1.4` OID 选择 KEM 证书算法。

`crypto/tls/pq_kex.go` 已经改为通过 `crypto/pq` 注册表查找算法；只有
`Kyber768` 保留一条旧 CIRCL 兼容分支。新增 KEM 走注册表，不进入该分支。

## 2. C 描述符

`pqc/include/pq_alg.h` 是唯一 ABI。KEM 必须提供：

```c
const pq_alg my_kem = {
    .abi_version = PQ_ALG_ABI_VERSION,
    .kind        = PQ_KIND_KEM,
    .input       = PQ_INPUT_MESSAGE,
    .flags       = 0,                 /* 占位实现才用 PQ_FLAG_PLACEHOLDER */
    .name        = "MY-KEM-768",      /* 稳定标识，TLS 配置用这个名字 */
    .oid         = "1.3.6.1.4.1.XXXX.1", /* 证书 .1.4 用这个 OID */
    .tls_code    = 0,                 /* KEM 证书算法可留 0；标准 group 再填 */
    .version     = "1.0",
    .pk_len      = ...,
    .sk_len      = ...,
    .ct_len      = ...,
    .ss_len      = 32,
    .keygen      = my_keygen,
    .pub_from_sk = my_pub_from_sk,
    .encaps      = my_encaps,
    .decaps      = my_decaps,
};
```

约束：

- 所有输出缓冲区由调用方分配；长度不匹配返回 `PQ_ERR_BUFFER`；
- `keygen` 必须同时输出 `pk` 和 `sk`；`pub_from_sk` 必须能由 `sk` 还原 `pk`，
  KEM 证书/`pqkemkey` 依赖它；
- `encaps` 输出 `ct` 和 `ss`；`decaps` 输出 `ss`；
- 函数必须可重入、线程安全，不保留输入指针；
- `name`、`oid`、`tls_code` 一旦用于配置/证书就不要再改；
- 建议 `ss_len = 32`，并明确是否对共享秘密做 KDF。

## 3. 注册

静态：

```c
/* pq_registry.c */
extern const pq_alg my_kem;
static const pq_alg *const pq_builtin[] = {
    ...,
    &my_kem,
};
```

动态（插件，启动前）：

```c
pq_alg_register(&my_kem);
```

## 4. TLS 配置

```bash
# KEX / ServerKeyGen
KEMTLS_KEX_ALG=MY-KEM-768

# KEM 证书路径
KEMTLS_KEM_ALG=MY-KEM-768
KEMTLS_KEM_KEY=pqcerts/end-entity-pq-key-KEM.bin
```

证书生成：

```sh
.build/pqkemkey -alg MY-KEM-768 -out /tmp/my-kem
.build/pqcertlab -alg Dilithium2 \
  -pub server-sig.pub -client-pub client-sig.pub \
  -kem-pub /tmp/my-kem.pub -client-kem-pub /tmp/my-kem-client.pub \
  -kem-oid 1.3.6.1.4.1.XXXX.1 -out /tmp/my-certs
```

`pqcertlab` 只把 OID 写进 `.1.4`，不关心算法实现；`myx509` 通过
`pq.ByOID` 找回描述符。

## 5. 已验证的 C 路径

本轮用现有 `PLACEHOLDER-KEM` 走了一遍“纯 C 注册表”路径：

```bash
KEMTLS_KEX_ALG=PLACEHOLDER-KEM
KEMTLS_PROTOCOL_TYPE=13
```

握手成功。说明新增 C KEM 只需注册，不需要改 TLS 的 KEX/ServerKeyGen 代码。

## 6. Go 实现的 KEM

ML-KEM 是 Go 标准库实现，放在 `pqc/mlkem.go` 和 GOROOT 的
`crypto/pq/mlkem.go`。后续如果也有 Go 实现：

- 复制 `mlkem.go` 的 `goKEMBackend` 模式，注册到 `goKEMAlgorithms`；
- 或提供 C 适配器，走上面的 C 路径（推荐，TLS 侧完全无感）。

当前没有导出 `pqc.RegisterKEM`；如果后续两种 KEM 都是 Go 实现，可以再加一个
公开注册函数，但 C 路径已经能覆盖“不改 TLS”的要求。

## 7. 标准化检查清单

每个新 KEM 接入前确认：

- [ ] 算法名、版本、OID、TLS code/group 已固定；
- [ ] `pk/sk/ct/ss` 长度与测试向量一致；
- [ ] 有 FIPS/规范 KAT 或至少交叉实现 KAT；
- [ ] `pub_from_sk` 可逆；
- [ ] 错误密文、截断、错误长度能被拒绝；
- [ ] 证书 `.1.4` OID 和 TLS 配置名一致；
- [ ] `pqc` 测试、`pqclist`、`pqkemkey`、`pqcertlab` 均能识别；
- [ ] 矩阵至少覆盖：KEX、ServerKeyGen、KEM 证书、Sig-KEM、KEM-Sig、
      PQ 链开关；
- [ ] 文档记录私有/标准码点，避免把私有值当成 IANA 标准。

## 8. 两种新 KEM 的建议接入顺序

1. 先接 KEX（`KEMTLS_KEX_ALG`），跑 type 11/13；
2. 再接 KEM 证书（`.1.4` OID + `KEMTLS_KEM_ALG`），跑 type 20/21；
3. 最后跑 Sig-KEM/KEM-Sig 和 PQ 链组合；
4. 每个算法至少保留一组固定密钥/密文的负例。
