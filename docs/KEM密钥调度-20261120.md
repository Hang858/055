# KEM 共享秘密进入应用密钥调度（阶段 2）

日期：2026-11-20
对应论文：第 4 章 4.4（异构认证的密钥派生，`K=H(pkI,pkR,ke,ce,cI,kI)`）

## 1. 改动

### 1.1 混入点

KEM 证书模式（认证编号 `20`）下，在拿到两段 KEM 共享秘密之后，把 master secret
替换为：

```
master' = HKDF-Extract(salt = master, IKM = kemSecretInput)
kemSecretInput = uint16(len(ssServer)) || ssServer || uint16(len(ssClient)) || ssClient
```

然后从 `master'` 派生：

- `client_application_traffic_secret_0`
- `server_application_traffic_secret_0`
- `exporter_master_secret`
- `resumption_master_secret`

握手流量密钥（`c hs traffic` / `s hs traffic`）**不混入**，因为服务端 Finished 必须
先于客户端证书/KEM 贡献发送，此时服务端还拿不到任何 KEM 秘密；这与 KEMTLS 的
时序约束一致。

实现位置：

- `crypto/internal/fips140/tls13/tls13.go`：`MasterSecret.WithKEMSecret`
- `crypto/tls/key_schedule.go`：`kemSecretInput`
- `crypto/tls/handshake_server_tls13.go`：`deriveKEMApplicationSecrets`，
  在 type 252 发送之后、session ticket 之前调用
- `crypto/tls/handshake_client_tls13.go`：`deriveKEMApplicationSecrets`，
  在收到 type 252 之后、发送 client Finished 之前调用

### 1.2 时序

```
ServerHello ... ServerFinished        (握手密钥)
        <-- client Certificate / CertificateVerify
type 252 (server -> client cert KEM ct)   (握手密钥)
        --> client Finished                (握手密钥 + kemFinishedHash)
session ticket                          (应用密钥，已混入 KEM ss)
```

- 服务端先发 252，再安装应用写密钥；否则 252 会被应用密钥加密，客户端无法解密。
- 客户端先读 252，再安装应用读密钥；client Finished 仍用握手密钥发送。
- `kemFinishedHash` 保留，KEM ss 同时约束 Finished 与应用密钥。

## 2. 测试

构建：`CGO_ENABLED=1`，GOROOT 指向打过补丁的 Go。

KEM 四种组合（20/21/22/23）全部握手成功，双方日志都有
`KEM 应用密钥已混入 ss_server=32 ss_client=32`，应用数据收发正常。

负向：

| 场景 | 结果 |
|---|---|
| 客户端 KEM 私钥错误 | 服务端 `tls: invalid client finished hash`；客户端本地握手返回成功，但首次读应用数据 `bad record MAC` |
| 服务端 KEM 私钥错误 | 同上 |
| 客户端缺少 KEM 私钥 | `KEM server ciphertext decapsulation failed` |

说明：TLS 1.3 客户端发送 Finished 后即返回，不等待服务端确认，所以错误密钥场景下
客户端可能先打印 `TLS handshake OK`，随后在应用数据阶段失败；服务端一定在
Finished 校验处失败。

回归：

- 协商矩阵 12/12（`docs/协议类型协商-20261120.md`）。
- 签名矩阵 10/10（`pqsig/run-tls-matrix.sh`），非 KEM 路径的密钥调度未变化。

## 3. 边界

- 应用密钥现在包含 KEM 秘密，但**握手密钥仍只来自 ECDHE**；这不是完整 KEMTLS
  密钥调度，KEM 证书模式仍是“ECDHE 握手 + KEM 认证/密钥绑定”。
- 服务端在 KEM 模式下不再发送 0.5-RTT 应用数据（应用密钥延迟到客户端证书之后）。
- 会话恢复（PSK）会用混入 KEM 秘密的 resumption secret；但恢复握手本身不重新
  做 KEM 认证，生产环境应禁用 KEM 模式的 resumption 或单独评估。
- 证书链的 PQ 签名仍未验证；KEM 公钥的授权仍依赖证书的经典签名。
- 未实现纯 KEM（去掉 ECDHE）模式。
