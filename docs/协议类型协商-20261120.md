# ProtocolType 协商与兼容回退（阶段 1）

日期：2026-11-20
对应论文：第 5 章 5.2/5.3（迁移模式矩阵、协商、回退）

## 1. 改动内容

### 1.1 客户端支持列表

新增私有扩展 `0xFFF3`（`extensionProtocolTypeList`），ClientHello 携带本端支持的
`ProtocolType` 列表，首项为首选。原有 `0xFFF1`（首选类型）和 `0xFFF2`（是否强制）
保持兼容。

- 客户端不发送列表时，服务端按 `[ProtocolType]` 处理，旧实现行为不变。
- 列表最多 32 项，非法值在服务端直接告警。
- 协议类型仍按 `10*认证 + 密钥交换` 编码：认证 `0/10/20`，密钥交换 `0/1/2/3`。

### 1.2 兼容语义

新增配置：

```go
ProtocolTypes         []uint16 // 本端支持列表，首项为首选
ModeCompatibilityFlag bool     // true=愿意跟随对端类型，并允许回退 ClassicAKE
```

语义与论文 `modeCompatibilityFlag` 对齐：

| 配置 | 行为 |
|---|---|
| 设置了 `ProtocolTypes`，`ModeCompatibilityFlag=true` | 列表自动补 `0`，协商时按客户端优先级选共同类型 |
| 设置了 `ProtocolTypes`，`ModeCompatibilityFlag=false` | 只接受本端首选；对端没提供时回退 `0`；双方都没有共同项则失败 |
| 未设置 `ProtocolTypes` | 沿用旧 `ProtocolTypeStrict`（1=强制），避免破坏已有部署 |

原 `ProtocolTypeStrict` 保留为旧接口，不再用于新配置。

### 1.3 协商规则

服务端在 `processClientHello` 中调用 `negotiateProtocolType`：

1. 候选按客户端列表顺序排列（论文的“客户端优先”）。
2. 过滤服务端不支持的、服务端不具备运行能力的类型。
3. 服务端强制模式下只接受本端首选或 `ClassicAKE`。
4. 客户端强制模式下服务端只能选客户端首选或 `ClassicAKE`。
5. 交集为空则发 `handshake_failure`，不再静默走经典 TLS。
6. 客户端校验 ServerHello 的选择必须在自己通告的列表里，否则发
   `illegal_parameter`，用于防降级。

### 1.4 组合补齐

| 组合 | 路径 | 状态 |
|---|---|---|
| 0/1/2/3 | 经典证书 + 经典/混合/HRR/ServerKeyGen | 可用 |
| 10/11/12/13 | PQ 签名证书 + 四种密钥交换 | 11/12/13 已测；10 继承原逻辑 |
| 20/21/22/23 | KEM 证书 + 四种密钥交换 | 20/21/22/23 已测 |

HRR（2/12/22）改为选择客户端尚未发送 key_share 的经典曲线，避免
`X25519MLKEM768` 无法在 HRR 中重发的问题；HRR 的 ServerHello 也携带完整组合
编号（而不是只带 `2`），客户端才能校验认证分支没有被降级。

`signature_algorithms_cert` 在打补丁的 Go 中本来就已发送（`defaults.go` 包含
Dilithium/SLH-DSA 私有码点），本次在服务端能力判断中使用它：客户端若声明了证书
验签算法列表但不含任何 PQ 签名，服务端不会选择 PQ 签名证书认证。

## 3. 边界

- 异构双向认证（一端签名证书、一端 KEM 证书）仍未支持：一个 `ProtocolType` 仍然
  同时描述双方，论文 4.4 的 Sig-KEM/KEM-Sig 需要拆成 `client_auth`/`server_auth`。
- HRR（2/12/22）只是对照路径；论文主张用 ServerKeyGen 避免 HRR，不把它作为推荐
  部署模式。
- KEM 共享秘密已由阶段 2（`docs/KEM密钥调度-20261120.md`）混入应用流量密钥。
- 证书链的 PQ 签名仍未验证；`signature_algorithms_cert` 只用于能力判断。

## 4. 应用

补丁：`packaging/tls-source/patches/protocol-mode-negotiation.patch`

应用顺序：

```bash
patch -p1 < slhdsa-tls-handshake.patch
patch -p1 < kem-registry-tls.patch
patch -p1 < protocol-mode-negotiation.patch
```

应用后需要重新构建 server/client；构建时保持 `CGO_ENABLED=1`（`crypto/pq` 通过
cgo 调 C 注册表）。

测试配置（两个测试程序都支持）：

```bash
KEMTLS_PROTOCOL_TYPE=23 \
KEMTLS_PROTOCOL_TYPES=23 \
KEMTLS_MODE_COMPAT=1 \
KEMTLS_KEM_ALG=PLACEHOLDER-KEM \
KEMTLS_KEM_KEY=... \
./server
```
