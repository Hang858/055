# 指标 2 · TLS 协议达到 128、256 比特量子安全等级的论证

TLS 协议用于为应用层协议提供加密传输与身份认证。对于 TLS 协议，其主要交互过程包括通信双方的密钥交换和身份认证，交互逻辑如下：

1) 客户端和服务端先进行算法协商，包括协议版本、密码套件、密钥交换算法、签名算法等，同时交换随机数。

2) 根据协商的密钥交换算法协商共享密钥。客户端在 key_share 中发送本机份额，服务端在 ServerHello 中返回本机份额（客户端未提供所需份额时先回 HelloRetryRequest），双方各自计算共享秘密并送入 TLS 1.3 的 HKDF 密钥调度，派生握手流量密钥。

3) 服务端在加密信道中发送证书（Certificate）和对握手报文的签名（CertificateVerify），客户端验签，对服务端身份进行认证。

4) 如果采用双向认证，服务端通过 CertificateRequest 要求客户端出示证书，客户端发送认证公钥和签名，服务端验签，对客户端身份进行认证。

5) 握手完成后由主密钥派生应用流量密钥，开启加密通信。

TLS 协议的抗量子，需要在协议的密码原语中加入抗量子密码，包括在密钥交换阶段加入抗量子密钥交换以及身份认证过程加入抗量子签名认证，具体如下：

1) 算法协商阶段，密钥交换算法列表加入抗量子/混合密钥交换，签名算法列表加入抗量子/混合签名算法，证书中承载抗量子公钥。

2) 根据协商的密钥交换算法协商共享密钥。对于混合密钥交换，客户端同时发送经典公钥和抗量子 KEM 公钥，两者按 RFC 9954 直接拼接、不带长度字段；服务端使用客户端经典公钥和本机经典私钥计算得到经典共享密钥 K_CL，使用客户端抗量子 KEM 公钥进行抗量子封装，得到抗量子封装密文和抗量子共享密钥 K_PQ，并将本机经典公钥和抗量子封装密文拼接后返回；客户端用同样方式计算得到 K_CL，并使用本机抗量子 KEM 私钥解封装得到 K_PQ。与 SSH 不同，TLS 不再做一次 K=HASH(K_CL||K_PQ)，而是把 K_CL||K_PQ 直接作为 (EC)DHE 输入送入 TLS 1.3 的 HKDF 密钥调度，派生得到握手密钥与应用流量密钥，经典密钥交换和抗量子密钥封装任何一方未被攻破，都能保证共享密钥的安全。TLS 的密钥交换阶段由抗量子 KEM 原语提供了量子安全能力，该阶段还使用哈希算法进行密钥派生，因此该阶段的量子安全等级取决于抗量子 KEM 算法和哈希算法的量子安全等级。经典分量也可采用国产密码算法 SM2，此时即"SM2 公钥（65 字节）与抗量子封装公钥""SM2 密文（129 字节）与抗量子封装密文"的拼接，构成国密混合。

3) 密钥交换过程中，服务端在 Certificate 中发送主机证书（含签名公钥），在 CertificateVerify 中给出对握手报文的签名，客户端验签，对服务端身份进行认证。对于混合签名，服务端同时提供经典签名公钥（ECDSA 或国产 SM2）和抗量子 DSA 公钥，并给出两种签名。客户端要同时验证经典签名和抗量子签名，两者均验证通过，才认为服务端身份认证通过。服务端认证阶段由抗量子 DSA 提供了量子安全能力，该阶段的量子安全等级取决于抗量子 DSA 算法的量子安全等级。

4) 对于采用双向认证的客户端，客户端同样发送认证公钥和签名，服务端要同时验证其经典签名和抗量子签名，两者均验证通过，才认为客户端身份认证通过。客户端认证阶段由抗量子 DSA 提供了量子安全能力，该阶段的量子安全等级取决于抗量子 DSA 算法的量子安全等级。

综上所述，要保证 TLS 协议可达到 128、256 比特量子安全，密钥交换和身份认证都应该达到 128、256 比特量子安全等级，即密钥交换过程的抗量子 KEM 原语的算法构造实例可达到 128、256 比特量子安全等级，身份认证过程的抗量子 DSA 原语的算法构造实例可达到 128、256 比特量子安全等级。本课题具体采用 ML-KEM-512/1024、HQC-128/256 与 ML-DSA-44/87，并以 SM2 作为经典分量混合使用。
