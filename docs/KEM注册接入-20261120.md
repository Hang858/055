# KEM 注册机制接入 TLS

日期：2026-11-20
范围：把 C 语言 KEM 的统一注册接口接入补丁版 GOROOT 的 KEM 证书路径，并用占位 KEM 跑通握手。

## 1. 结构

```text
pqc/                          # 独立 C/Go 注册框架（可单测）
  include/pq_alg.h
  pq_registry.c
  pq_placeholder.c
  pq_bit_placeholder.c
  pqc.go
  cmd/pqclist
  cmd/pqkemkey

$GOROOT_PQ/src/crypto/pq/     # 同一套 C/Go 文件，包名 pq
$GOROOT_PQ/src/crypto/myx509  # 通过 crypto/pq 查 KEM 算法
$GOROOT_PQ/src/crypto/tls     # KEMTLSKEMAlg / KEMTLSKEMKey
```

`pq_alg` 同时描述签名与 KEM，靠 `kind` 区分：

- `PQ_KIND_SIG`：`keygen / pub_from_sk / sign / verify`
- `PQ_KIND_KEM`：`keygen / pub_from_sk / encaps / decaps`

查找入口只有 `pq_alg_lookup(name)`；Go 侧只有 `pqc.Lookup(name)`。

## 2. KEM 证书扩展

- `.1.0`：KEM 公钥（原始字节）
- `.1.4`：KEM 算法 OID（DER），新增
- `.1.3`：仍只表示 PQ **签名**算法，不用于 KEM

`myx509.EncryptionFromCert`：

1. 有 `.1.4`：按 OID 查 `pq.Lookup`，`ParsePublicKey` 后 `Encapsulate`；
2. 无 `.1.4`：保持旧 Kyber768 行为。

`myx509.QuantumDecryptionWithLocalKeyAlg` 按配置的算法名查注册表并 `Decapsulate`。

## 3. TLS 配置

`crypto/tls.Config` 新增：

```go
KEMTLSKEMAlg string
KEMTLSKEMKey string
```

应用通过环境变量传入：

```sh
KEMTLS_KEM_ALG=PLACEHOLDER-KEM
KEMTLS_KEM_KEY=/path/to/kem.priv
```

为空时保持旧 Kyber768 路径。KEM 私钥缺失、密文长度错误、解封装失败现在都会发 alert
并终止，不再忽略错误。

## 4. 证书工具

`pqsig/cmd/pqcertlab` 新增：

```text
-kem-pub        服务端叶证书的 KEM 公钥
-client-kem-pub 客户端叶证书的 KEM 公钥
-kem-oid        KEM 算法 OID
```

`pqc/cmd/pqkemkey` 通过注册表生成原始 KEM 密钥对：

```sh
cd pqc
go build -o ../.build/pqkemkey ./cmd/pqkemkey
../.build/pqkemkey -alg PLACEHOLDER-KEM -out /tmp/server-kem
```

生成 KEM 证书示例：

```sh
.build/pqcertlab -alg Dilithium2 \
  -pub server-sig.pub -client-pub client-sig.pub \
  -kem-pub server-kem.pub -client-kem-pub client-kem.pub \
  -kem-oid 1.3.6.1.4.1.54321.99.2 -out /tmp/kem-certs
```

## 5. 实测

### 5.1 KEM 证书握手

用 `ProtocolType=QuantumSupportKemCert_KEX`（21）重新编译 cloudflare server/client，
服务端和客户端分别设置自己的 KEM 私钥：

```text
KEMTLS_KEM_ALG=PLACEHOLDER-KEM
KEMTLS_KEM_KEY=.../srv-kem.priv  # 服务端
KEMTLS_KEM_KEY=.../cli-kem.priv  # 客户端
```

结果：

```text
总次数: 1
平均耗时: 4.98623ms
TLS handshake OK, server verified
Client sent: Hello TLS Server
Client received: Hello TLS Server
```

说明：

- 客户端用服务端证书 `.1.0` + `.1.4` 封装；
- 服务端解封装后，用客户端证书 `.1.0` + `.1.4` 再封装，通过 type 252 回送；
- 客户端按实际 `1+3` 字节头解析密文，不再写死 Kyber768 长度。

负例现状：

- 缺 KEM 私钥文件、密文长度错误会失败并返回 alert；
- 错误客户端 KEM 私钥：客户端 Finished 校验失败，服务端报
  `tls: invalid client finished hash`；
- 错误服务端 KEM 私钥：同样在客户端 Finished 处失败。

原因是本补丁把 `ss_server` 和 `ss_client` 绑定进了 **client Finished** 的派生键：
双方在 252 消息之后用 `kemFinishedHash` 计算 client Finished。这样错误 KEM 私钥不能
通过握手，KEM 证书具备了认证意义。但它仍然**没有进入 TLS key schedule**，应用数据密钥
仍来自 ECDHE。

### 5.2 回归

- `pqsig/run-tls-matrix.sh`：**10/10**
- `kemtls-lab/run-tests.sh`：**20/20**
- `pqc` 单测：`ok pqc`

构建这些程序时使用 `CGO_ENABLED=1`，因为 `crypto/pq` 通过 cgo 调用 C 注册表。

## 6. 仍未完成：KEM 共享密钥进入 key schedule

当前 KEM 证书模式：

- 双方都算出了 `persistentssKEM` / `persistentssKEM_Client`；
- 这两个值已经绑定到 **client Finished**（`kemFinishedHash`），错误私钥会失败；
- 但 `key_schedule.go` 的 Handshake/Master secret 仍只使用 ECDHE；
- 双向 CertificateVerify 仍是 RSA；
- 因此它具备“KEM 证书认证 + RSA 认证”，但应用数据密钥没有 KEM 贡献，不是完整的
  KEMTLS 密钥调度。

要完成完整 KEMTLS，需要把 KEM SS 在明确的握手阶段混入 Handshake/Master secret，
并补充篡改密文、重放、降级、KEM 私钥替换等负例。该问题独立于本次“C 算法注册接口”改造。
