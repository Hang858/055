# 双维度认证与异构握手（阶段 4）

日期：2026-11-20
对应论文：大论文第 4 章 4.4（Sig-KEM、KEM-Sig 异构认证）；第 5 章 `(auth,kex)`
坐标的双维度扩展。

## 1. 目标

在保留大论文 `ProtocolType` 模式矩阵、1.5-RTT 和回退逻辑的前提下，把认证从
“双方同一个 auth”扩展为：

```
(client_auth, server_auth, kex)
```

- `client_auth == server_auth`：退化为原有同构模式，现有 `ProtocolType` 不变；
- `(Sig,KEM)`：Sig-KEM；
- `(KEM,Sig)`：KEM-Sig；
- 另外保留 Sig-Sig、KEM-KEM。

小论文 FA-TLS 的 `fa_auth_modes` 是同一思路；本轮采用大论文的单阶段密钥调度，
没有实现 FA-TLS 的两阶段 AHS。

## 2. 协商

新增私有扩展 `0xFFF4`（`extensionAuthModes`），载荷：

```
uint16 client_auth
uint16 server_auth
```

- ClientHello 携带客户端自己的认证和期望的服务端认证；
- ServerHello 回显最终选择；
- 同构模式也回显，便于客户端校验。

`Config` 新增：

```go
ClientAuthMode uint16 // 客户端自己的认证：0/10/20
ServerAuthMode uint16 // 期望服务端的认证：0/10/20
```

0 表示按 `ProtocolType` 的认证位推导。服务端不读取这两个字段，而是按
ClientHello 通告值协商。

协商规则：

1. 客户端按 `ServerAuthMode` 过滤 `ProtocolTypes`，只保留认证位匹配的类型和
   `ClassicAKE`；
2. 服务端在候选类型上再要求 `protocolTypeAuth(t) == ServerAuthMode`；
3. 服务端检查自己能否接受 `ClientAuthMode`（`ClientAuth >= RequestClientCert`）；
4. 没有共同类型时按现有规则回退 `ClassicAKE(0)`；
5. 客户端校验回显的 `(client_auth, server_auth)`，不一致则中止；
6. 旧服务端不识别扩展时，只允许同构模式继续。

## 3. 四种模式的 KEM 方向

| 模式 | client_auth | server_auth | ss_server | ss_client | type 252 | client Finished |
|---|---|---|---|---|---|---|
| Sig-Sig | Sig | Sig | — | — | 否 | 标准 |
| KEM-KEM | KEM | KEM | 有 | 有 | 是 | 两段都绑定 |
| Sig-KEM | Sig | KEM | 有 | — | 否 | 绑定 ss_server |
| KEM-Sig | KEM | Sig | — | 有 | 是 | 绑定 ss_client |

- `server_auth == KEM`：客户端向服务端 KEM 证书封装，密文放在客户端
  `Certificate` 消息的 `persistentCiphertextKEM` 字段；服务端解封装。
- `client_auth == KEM`：服务端向客户端 KEM 证书封装，通过私有 `type 252`
  发送；客户端解封装。
- 应用密钥派生在两段 KEM 秘密中至少有一段时执行；`kemFinishedHash` 也按
  实际存在的段绑定，缺失段按空串编码。

## 4. 证书与签名

- `server_auth == Sig`：服务端发 PQ 签名证书 + PQ `CertificateVerify`；
- `server_auth == KEM`：服务端发 KEM 证书，`CertificateVerify` 仍用 RSA 证书键；
- `client_auth == Sig`：客户端发 PQ 签名证书 + PQ `CertificateVerify`；
- `client_auth == KEM`：客户端发 KEM 证书，`CertificateVerify` 用 RSA 证书键；
- 客户端签名是否走 PQ，按 `client_auth == Sig` 判断，不再只看 `KEMTLS_SIG_ALG`。

证书链 PQ 验签（阶段 3）仍然可选，异构模式没有强制打开。

## 5. 测试

四模式（本机、KEM 使用 PLACEHOLDER-KEM，Sig 使用 Dilithium2）：

| 模式 | 结果 | 协商值 |
|---|---|---|
| Sig-Sig | PASS | auth=(10,10) |
| KEM-KEM | PASS | auth=(20,20) |
| Sig-KEM | PASS | auth=(10,20)，ss_server=32/ss_client=0 |
| KEM-Sig | PASS | auth=(20,10)，ss_server=0/ss_client=32 |

负向与回退：

| 场景 | 结果 |
|---|---|
| 客户端要 Sig-KEM（21），服务端只支持 Sig-Sig（11） | 回退 `ClassicAKE(0)`，握手成功 |
| 客户端不回退（列表不含 0） | `handshake failure` |
| Sig-KEM 服务端 KEM 私钥错误 | 服务端 `invalid client finished hash` |
| KEM-Sig 客户端 KEM 私钥错误 | 服务端 `invalid client finished hash` |

回归：

- 同构协商矩阵：12/12；
- 签名矩阵：10/10；
- `go test -run 'TestAuth|TestProtocolType|TestKEM|TestWithKEM' crypto/tls`：通过。

## 6. 边界

- 仍是**单阶段**密钥调度：KEM 秘密进入 master/应用密钥和 Finished，但没有
  FA-TLS 的 AHS 认证握手 epoch，也没有独立的 `KEMEncapsulation` 消息；
- KEM 密文仍复用 `Certificate` 字段和 `type 252`，不是 FA-TLS 的 wire format；
- 服务端 `CertificateVerify` 在 KEM 模式仍用 RSA 证书键（TLS 1.3 要求有
  CertificateVerify），不是纯 KEM 认证；
- 认证模式只有 0/10/20 三种，没有按算法/证书链细分；
- PQ 链验签和异构模式可以组合，但未做组合矩阵。

## 7. 应用

补丁：`packaging/tls-source/patches/heterogeneous-auth.patch`

顺序：

```bash
patch -p1 < slhdsa-tls-handshake.patch
patch -p1 < kem-registry-tls.patch
patch -p1 < protocol-mode-negotiation.patch
patch -p1 < kem-key-schedule.patch
patch -p1 < pq-certificate-chain.patch
patch -p1 < heterogeneous-auth.patch
```

应用环境变量：

```bash
KEMTLS_CLIENT_AUTH=10   # 客户端自己的认证
KEMTLS_SERVER_AUTH=20   # 期望服务端的认证
```

示例：

- Sig-KEM：`ProtocolType=21`，`CLIENT_AUTH=10`，`SERVER_AUTH=20`；
- KEM-Sig：`ProtocolType=11`，`CLIENT_AUTH=20`，`SERVER_AUTH=10`。
