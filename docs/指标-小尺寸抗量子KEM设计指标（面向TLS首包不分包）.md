# 指标（草案）：面向 TLS 首包不分包的小尺寸抗量子 KEM 算法设计

## 一、指标表述

**场景（一句话）**：应用场景为 TLS 握手客户端发出的第一个报文 ClientHello——该报文一旦超过单个
TCP 段（以太网 MTU 1500 下 TLS 记录上限约 1455 字节）或单个 QUIC/DTLS 数据报（约 1200 字节）
就会发生分包，丢包时握手至少多消耗 1 个 RTT，并可能因中间盒/负载均衡无法正确处理大 ClientHello
而造成握手变慢甚至连接中断；而抗量子 KEM 的封装公钥正是 ClientHello 中体积占比最大的部分。

**指标（一句话）**：设计小尺寸抗量子 KEM 算法，在 NIST 安全类别 3（192 比特量子安全等级）与
类别 5（256 比特量子安全等级）下，**封装公钥分别不超过 1024 字节与 1200 字节、封装密文分别不超过
1024 字节与 1200 字节**，使携带该 KEM 密钥交换公钥（key_share）的 TLS ClientHello 在线长度不超过 1460 字节（记录
长度字段不超过 1455 字节，可装入以太网单个 TCP 段，不发生分包）；并进一步以封装公钥 ≤ 960 字节为目标，使其可装入 1200 字节的 QUIC/DTLS
单个数据报。

**指标简短版（可直接入表）**：在 NIST 安全类别 3 / 5 下实现封装公钥 ≤ 1024 / ≤ 1200 字节、
封装密文 ≤ 1024 / ≤ 1200 字节的抗量子 KEM，保证 TLS ClientHello 携带该 KEM 密钥交换公钥时单报文传输
（在线 ≤1460 字节）不分包。

## 二、为什么现有标准算法"差点意思"

TLS 1.3 的 ClientHello 需要在 supported_groups 中声明抗量子（或混合）密钥交换算法，并在 key_share
中给出**客户端侧的密钥交换公钥，即 KEM 的封装公钥**，该公钥构成 ClientHello 体积的主要增量。
在只携带一个抗量子密钥交换公钥时，`ClientHello 在线字节数 ≈ 封装公钥长度 + 其他开销`，其中"其他开销"
**不是固定值**：本仓库客户端实测为 **189~199 字节**（1~6 个 supported_groups，明细见
`docs/背景-PQC-TLS首飞行分包与ClientHello体积.md` 第三节），浏览器客户端通常为 300~400 字节。
据此反推"不分包"对公钥尺寸的预算（下列上限按本仓库客户端的 199 字节开销计算）：

| 传输载体 | 单报文容量（在线字节） | 扣除其他开销后的公钥预算 |
|---|---|---|
| 以太网 TCP（MSS 1460） | ClientHello 在线 ≤ 1460 字节（记录长度字段 ≤1455） | 封装公钥 ≤ 约 **1261 字节** |
| QUIC / DTLS 单数据报（1200 字节） | ClientHello 在线 ≤ 约 1160 字节（扣除 QUIC Initial 头与 CRYPTO 帧开销） | 封装公钥 ≤ 约 **961 字节** |

（若换用其他客户端，需把上表中的"199 字节"替换为实测开销重新推算。）

对照现有标准抗量子 KEM 的实际尺寸（公钥 / 密文）：

| 算法 | NIST 安全类别 | 量子安全等级 | 封装公钥（字节） | 封装密文（字节） | 公钥+密文 |
|---|---|---|---|---|---|
| ML-KEM-512（FIPS 203） | 1 | 128 比特 | 800 | 768 | 1568 |
| ML-KEM-768（FIPS 203） | 3 | 192 比特 | 1184 | 1088 | 2272 |
| ML-KEM-1024（FIPS 203） | 5 | 256 比特 | 1568 | 1568 | 3136 |
| HQC-128 | 1 | 128 比特 | 2249 | 4433 | 6682 |
| HQC-192 | 3 | 192 比特 | 4522 | 8978 | 13500 |
| HQC-256 | 5 | 256 比特 | 7245 | 14421 | 21666 |

可以看出差距所在：**ML-KEM-512 体积够小但只有 128 比特等级**；达到 192 比特的 **ML-KEM-768
（1184 字节）在 QUIC/DTLS 的单个 1200 字节数据报里已经装不下**；达到 256 比特的
**ML-KEM-1024（1568 字节）连以太网单个 TCP 段都装不下**，必然分包；**HQC 系列（2249~7245 字节）
则远远超出**。也就是说，在 192/256 比特量子安全等级上，现有标准算法没有一款能同时满足"量子安全"
与"ClientHello 单报文不分包"两个条件，这正是需要通过算法设计（更紧凑的参数与编码、更好的代数
结构或压缩表示）去突破的空间。

## 三、指标数值的取值依据与建议分档

按上表预算，建议按下述两档设定考核指标（"基础目标"保证以太网场景不分包；"进阶目标"进一步覆盖
QUIC/DTLS 单数据报场景）：

| 分档 | 安全类别 | 封装公钥 | 封装密文 | 相比标准算法的压缩幅度 | 效果 |
|---|---|---|---|---|---|
| 基础目标 | 类别 3（192 比特） | ≤ 1024 字节 | ≤ 1024 字节 | 公钥较 ML-KEM-768（1184）减小 ≥13.5% | ClientHello 在线 ≈1223 字节，≤1460，单段不分包 |
| 基础目标 | 类别 5（256 比特） | ≤ 1200 字节 | ≤ 1200 字节 | 公钥较 ML-KEM-1024（1568）减小 ≥23.5% | ClientHello 在线 ≈1399 字节，≤1460，单段不分包 |
| 进阶目标 | 类别 3（192 比特） | ≤ 960 字节 | ≤ 1024 字节 | 公钥较 ML-KEM-768 减小 ≥18.9% | ClientHello 在线 ≈1159 字节，可装入 QUIC/DTLS 1200 字节单数据报 |
| 进阶目标 | 类别 5（256 比特） | ≤ 960 字节 | ≤ 1024 字节 | 公钥较 ML-KEM-1024 减小 ≥38.8% | 同上，且覆盖 256 比特等级 |

若考核口径采用"公钥+密文总尺寸"，可取 **类别 3 ≤ 2048 字节、类别 5 ≤ 2400 字节**
（后者较 ML-KEM-1024 的 3136 字节减小 ≥23.5%）。

## 四、验证方式

指标可通过"尺寸声明 + TLS 实测"两条证据验证：一是算法设计文档中给出各参数集的公钥、私钥、密文、
共享秘密长度并与上表口径一致；二是把该 KEM 以混合或纯抗量子方式接入 TLS（key_share 中承载其封装
公钥），用抓包统计 ClientHello 的在线长度并断言 ≤1460 字节（记录长度字段 ≤1455；QUIC/DTLS 场景 ≤1200 字节），
即判定为"不分包"。本课题现有工具链可直接复用：`tools/tls_hello_check.py` 内置了各类混合组密钥交换公钥的
预期长度表，可对抓包直接断言 key_share 长度与 ClientHello 记录长度（例如本课题实测：
SM2Kyber512 混合组 key_share 865 字节时 ClientHello 在线 1064 字节、X25519Kyber1024 的 1600 字节对应 1789 字节、
HQC-128 的 2281 字节对应 2470 字节，与上述"公钥 + 189~199 字节开销"的规律一致）。

参考：FIPS 203（ML-KEM 参数集与安全类别）、HQC 规范（HQC-128/192/256 尺寸，HQC-192 公钥 4522、
密文 8978 字节）、RFC 9954 §4（抗量子算法可能使 ClientHello 大于单个报文）、RFC 9000 §14.1
（QUIC 初始数据报最小 1200 字节）、RFC 6928（初始拥塞窗口）、RFC 791（IPv4 最小 MTU 576 字节），
以及 Chrome 发布说明中关于 Kyber/ML-KEM 体积导致部分中间盒连接中断的提示。
