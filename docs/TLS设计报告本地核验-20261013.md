# TLS 设计报告本地核验（2026-10-13）

核验范围：根目录 `TLS (1).pdf` 第 5 章、`docs/superpowers/specs/2026-10-13-sm2-mldsa-tls-design.md`，以及二进制包 `dist/pqc-gateway-hybrid-ubuntu20.04-amd64-20261013.zip`。本机是 Ubuntu 24.04 / x86_64，处理器为 Intel Core i7-8750H；本记录不代表 Ubuntu 20.04 厂内实机或第三方测试结果。

| 核验项 | 本地证据与结果 | 结论 |
| --- | --- | --- |
| SM2＋ML-DSA-44/87 双签证书与双向认证 | 证书工具、网关全套测试通过；交付包 `smoke.py` 对 SM2Kyber、SM2HQC 的 44/87 四组完整连接均通过。 | 本地通过。 |
| 证书与签名拒绝路径 | `hybridcert` 测试覆盖错误 CA、SAN、有效期、用途、私钥不匹配、SM2/PQ 证书签名与握手签名的缺失或篡改。交付包验收拒绝缺客户端证书、错误档位和传统单签降级。 | 本地通过。 |
| 真实握手码点与密钥交换长度 | `tools/verify_tls_auth_wire.py` 将交付包的真实 TLS 字节经回环 TCP 转发器记录并解析。44 档 `signature_algorithms=0xfea0`、87 档 `0xfea1`；`probe` 在验证证书和 `CertificateVerify` 后报告相同码点。SM2Kyber512/1024 的 ClientHello/ServerHello `key_share` 长度分别为 865/897、1633/1697 字节；SM2HQC-128/256 分别为 2314/4562、7310/14550 字节。 | 本地通过；原始记录在 `dist/tls-design-verification-20261013/`。 |
| `signature_algorithms_cert` | 四组真实 ClientHello 均未发送此扩展；`crypto/tls` 当前只设置 `signature_algorithms`。[RFC 8446 §4.2.3](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.2.3) 允许两者策略相同时省略 `signature_algorithms_cert`，证书算法随前者约束。 | 与报告“显式写入”文字有差异，但不是 TLS 1.3 协议违规；若验收要求该扩展必须出现，需另行开发并记录握手复测。 |
| ServerHello 中的签名标记 | 设计报告第 5.3.4 节要求在 ServerHello 标记选中的混合签名；[TLS 1.3 的 ServerHello 结构](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.1.3) 没有这个字段。当前程序按协议在 `CertificateVerify.algorithm` 携带实际私有码点，客户端验证后写入连接状态。 | 设计报告的报文位置需修订，不能为了字面一致增加非标准 ServerHello 字段。 |
| 标准 ML-KEM 与旧 Kyber 区别 | 网关样例和实际 `cfkem.go` 仍选用 `SM2Kyber*Draft00`，后端是 CIRCL `kem/kyber`。交付程序的配置检查拒绝 `X25519MLKEM768` 和 `SM2MLKEM512`。补丁 TLS 栈虽有 `X25519MLKEM768`，网关配置未开放；没有 SM2＋ML-KEM-512/1024 组。[FIPS 203](https://csrc.nist.gov/pubs/fips/203/final) 定义的 ML-KEM 与预标准 Kyber [不能仅改名视为兼容](https://www.rfc-editor.org/rfc/rfc9935.html)。 | **TLS 网关的标准 ML-KEM 迁移未完成。**证书工具的 ML-DSA 后端与此是两条不同路径。 |
| 传统兼容与降级 | 交付包负例验证混合认证端口拒绝 ECDSA 客户端。传统 ECDSA 可在独立配置/端口运行。 | 强制混合认证通过；报告中的同端口自动回退未实现，且不应在强制混合策略下默认开启。 |
| 交付包 | 三个 Linux x86_64 静态程序、44/87 配置、联调证书、安装与验收说明齐全；`SHA256SUMS`、安装脚本和解压后 `smoke.py` 已在本机运行通过。 | 本地通过；厂内 Ubuntu 20.04 实机待测。 |

## 本机握手性能

执行 `BenchmarkMutualTLS`：每组 50 次全新 TLS 1.3 双向认证握手，重复 3 轮，禁用会话票据，包含服务端与客户端证书/握手双签验证。表中耗时与内存分配取 3 轮中位数；使用本机回环网络，不包含业务转发及跨机器网络时延。

| 交换组／身份签名 | 每次握手耗时 | 每次分配 | 每次分配次数 |
| --- | ---: | ---: | ---: |
| SM2Kyber512 / ML-DSA-44 | 24.10 ms | 1.05 MB | 约 16,050 |
| SM2Kyber1024 / ML-DSA-87 | 25.46 ms | 1.42 MB | 约 16,260 |
| SM2HQC-128 / ML-DSA-44 | 39.88 ms | 1.09 MB | 约 16,050 |
| SM2HQC-256 / ML-DSA-87 | 119.22 ms | 1.59 MB | 约 16,250 |

三轮原始耗时（ms/次）依次为：SM2Kyber512 `24.131、24.100、23.810`；SM2Kyber1024 `25.466、25.464、25.327`；SM2HQC-128 `39.875、39.877、39.486`；SM2HQC-256 `119.260、119.002、119.219`。另外，SM2＋ML-DSA 签名解析器的错误公钥和 DER 边界测试通过；对畸形签名输入做了 3 秒本地模糊测试，共执行 2,200 次，未接受错误签名。

设计报告第 5.6 节给出的弱网延迟和 CPU 增幅是估算值；上述本机数据不能证明那些百分比。正式验收需在指定网络、并发量和设备上测吞吐、CPU、内存峰值、握手失败率。需要厂内环境或第三方执行的项目未在本记录中标为通过。

## 复跑命令

从项目根目录执行；前两项使用第四阶段交付包里的程序，第三项使用项目的补丁 Go 工具链及本机 liboqs：

```sh
mkdir -p dist/tls-design-verification-20261013
unzip -q dist/pqc-gateway-hybrid-ubuntu20.04-amd64-20261013.zip \
  -d dist/tls-design-verification-20261013
cd dist/tls-design-verification-20261013/pqc-gateway-hybrid-ubuntu20.04-amd64-20261013
sha256sum -c SHA256SUMS
python3 smoke.py
cd ../../../
python3 tools/verify_tls_auth_wire.py \
  --bundle dist/tls-design-verification-20261013/pqc-gateway-hybrid-ubuntu20.04-amd64-20261013 \
  --output dist/tls-design-verification-20261013
```

基准测试命令见 `packaging/build_hybrid_runtime_release.py` 中的工具链环境设置；在 `gateway/` 运行 `go test -tags=pq_hqc,netgo,osusergo ./hybridcert -run '^$' -bench '^BenchmarkMutualTLS$' -benchtime=50x -benchmem -count=3`。需配置 `GOROOT`、`GOMODCACHE`、`CGO_CFLAGS` 和 `CGO_LDFLAGS` 指向本地补丁工具链与 liboqs。

TLS 1.3 报文中的 `CertificateRequest`、`Certificate` 和 `CertificateVerify` 在 ServerHello 之后受加密保护；本次 TCP 字节记录只直接解析明文 ClientHello/ServerHello。双签验证结果来自程序连接状态与破坏性握手测试，不能称作已解密的握手报文抓包。

补丁 Go 标准库的独立 `go test crypto/tls` 仍在编译期失败：遗留测试 `tls_cf_circl_test.go` 引用了未定义的 `x509.PureEdDilithium2`。这不影响上述网关模块测试及交付程序运行，但标准库测试套件尚不能作为通过证据。
